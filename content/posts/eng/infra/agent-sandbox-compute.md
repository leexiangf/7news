Agent 产品从「聊天」走到「代执行」之后，账单里会出现一条以前不显眼的线：**短生命周期执行环境的创建次数**。一次工具调用可能拉起容器 / microVM、注入密钥、挂只读文件系统、跑完即毁——日创建量上千万时，沙箱调度的体感会接近 GPU 排队。

本稿无单一厂商通稿可引，按工程观察写清机制与核对清单；勿把文中描述当成某家产品的发布声明。

## 为什么突然变贵、变难

| 旧假设 | Agent 场景下的现实 |
| --- | --- |
| 长驻服务、偶发扩缩 | 秒级创建 / 销毁，峰值由会话并发决定 |
| 镜像很少变 | 每任务可能装依赖，层缓存命中率决定冷启 |
| 密钥在服务侧常驻 | 按次注入、按次回收，泄漏窗口更短也更频繁 |
| 日志挂服务名 | 需要「单次运行」可回放，否则排障对不上工具调用 |

成本漏斗往往不是「模型贵一点」，而是：**冷启 × 创建频率 × 失败重试**。只盯 token 单价，沙箱口子会悄悄放大。

## 工程上要盯的四条线

**冷启动与镜像。** 基线镜像要薄；常用依赖预烘焙；层缓存与快照（若有）要进容量规划。核对：P50 / P95 创建到 ready 的时延，以及缓存命中率。

**网络与密钥边界。** 出站默认拒绝或白名单；密钥按次注入、任务结束即吊销；宿主机路径只读挂载。核对：无任务时密钥是否仍可读；沙箱能否扫到兄弟任务的卷。

**超时与费用封顶。** 单任务墙钟超时、CPU / 内存上限、日预算熔断；重试要有幂等键，避免「失败 → 再开沙箱」滚雪球。核对：人为拖死进程是否按策略杀；账单是否按租户可拆。

**可回放观测。** 每次运行绑定 run-id：命令、退出码、stdout/stderr 摘要、网络拒绝次数。核对：从一次失败的工具调用能否反查到完整沙箱生命周期。

## 和「推理算力」怎么并列看

GPU 池解决「模型算得动」；沙箱池解决「代码跑得安」。平台组若已上 Kinference / Gateway 一类推理控制面，沙箱侧仍缺对称物：限流、租户计量、队列深度、失败预算。没有控制面时，最先崩的通常是**创建 API 的 QPS 与镜像仓库**，而不是模型本身。

上线前用合成负载压一遍「空任务创建—注入—立刻销毁」路径；若这条路径的 P95 已经不可接受，再谈复杂 Agent 工作流只会更差。
