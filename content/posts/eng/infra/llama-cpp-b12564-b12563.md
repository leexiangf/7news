llama.cpp 在 **2026-11-20** 连续打出两个预发布构建标签。真正值得运维停下来看的是 **b12563** 的精度修复；同日稍后的 **b12564** 是 Orin 上的 MMVQ 微优化。二者无直接因果，只是同一条高频构建流上的相邻提交。

## b12563：为什么 per-expert 回退会丢精度

发布说明（PR [#31345](https://github.com/ggml-org/llama.cpp/pull/31345)）写明：per-expert 的 `dst_slice` 一直保持 `op = GGML_OP_NONE`，于是 `ggml_prec_get_acc` 返回 **UNDEFINED**，上层请求的累加精度被直接忽略。本版把该 slice 的 op 设为 **`GGML_OP_MUL_MAT`**，让精度请求重新生效。说明同时写明：**回滚**此前「量化 src0 走 fp32 结果缓冲」的方案，并移除相关测试——最终定案靠的是「op 正确」，而不是换一套输出 dtype。

## 哪条 CUDA 路径会炸成 inf

| 环节 | 行为 |
| --- | --- |
| IQ1_M 专家权重 | 没有对应 MMQ kernel |
| 批量较小时 | 走 MMVQ |
| 批量超过 MMVQ 上限 | dequantize + cuBLAS |
| 测试数值量级 | 约 **1.3e5**，高于 fp16 最大值 **65504** |
| 旧 fp16 结果缓冲 | 溢出成 **inf**，下一层再变 **NaN** |
| CPU 参考 | 仍保持有限值，便于对照 |

发布说明引用的现场案例是 **gpt-oss-120b** 使用 IQ1_M 专家、在 `-ub 512` 下运行（见讨论 [#30951](https://github.com/ggml-org/llama.cpp/issues/30951)）。新增用例**只挂在 CUDA 后端**：Vulkan 在默认精度下会有意以 fp16 累积量化矩阵乘，「按设计会失败」，因此不加入这组测试。

## b12564：Orin 单列 MMVQ

**b12564**（PR [#31268](https://github.com/ggml-org/llama.cpp/pull/31268)）优化 CUDA 上 Orin 的 single-column MMVQ，并在 `calc_rows_per_block` 为 Orin 建独立分支。它与 b12563 的精度故事相互独立：没有 Orin 设备的集群不必为 64 单独排期，但若你跟主线二进制，一次更新通常会同时吃到两个标签。

## 升级后怎么自证

1. 确认构建号 ≥ **b12563**（或已包含 #31345）。  
2. 用会产生超过 65504 中间值的 **IQ1_M / 大 `-ub`** 负载在 CUDA 上复测，输出应保持有限值。  
3. 同一模型与参数对比 **CPU 参考**，避免只看「能跑」而漏掉静默 NaN。  
4. 不要用 Vulkan 默认精度路径去「验证」这组 CUDA 用例——官方已说明不适用。

高频构建流里，多数标签是噪音；**b12563** 属于会把「偶发 NaN」收成可解释工程缺陷的那一类。Orin 用户可顺带确认 **b12564** 是否进入你使用的 artifact 渠道。
